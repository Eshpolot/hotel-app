# Hotel Alay Art — проверка и изменения (27.10.2026)

## Область проверки
Проверен код репозитория, SQL-схема, зависимости и локальная сборка. Это не полный пентест. Рабочая база, OAuth, почтовая доставка и настройки хостинга не проверялись и не изменялись. Наличие уязвимой политики в репозитории не доказывает, что она установлена в рабочей БД.

## Найдено и исправлено в коде / миграции

| Риск | Исправление |
|---|---|
| Критический: пользователь мог обновить `profiles.role` и стать администратором | Отозваны широкие права; разрешено менять только имя, телефон, аватар. Вставка профиля только через триггер регистрации. |
| Высокий: публичное чтение профилей | RLS: только свой профиль или администратор. |
| Высокий: цена, статус и параметры брони задавались клиентом | Ограничения колонок; серверный триггер рассчитывает цену, проверяет даты, вместимость, контакты. Заявка всегда `pending`. |
| Высокий: клиентская проверка пересечения видела только собственные брони | Удалена ложная проверка. Подтверждение администратором проверяет инвентарь в БД с блокировкой строки категории. Дата выезда не занимает следующую ночь. |
| Высокий: изменение любых полей собственной заявки | Гость может только отменить свою ожидающую заявку. Цена, даты, владелец защищены правами колонок. |
| Ошибки интерфейса: доступ к админке при пустом профиле; отмена отображалась успешной даже при ошибке API | Маршрут закрыт по умолчанию, проверяются ответы API. |
| Спам заявками | Лимит 5 заявок в час на аккаунт с транзакционной блокировкой. Это не заменяет CAPTCHA и внешние ограничения. |
| Зависимости: исходный npm audit — 11 проблем | Обновлены зависимости; итоговый npm audit — 0 известных проблем. |
| Неработающая production-сборка и Node-сервер | Исправлены minifier, ESM, зависимости сервера, fallback и кэширование. Заголовки безопасности ставятся до выдачи статики. |

Publishable key в браузере не является секретом. Защита данных должна обеспечиваться RLS, а не сокрытием ключа. Service-role ключи нельзя помещать в `VITE_*`.

## Новые возможности
- Каталог из БД вместо статичного массива; загрузка, ошибка, повтор и пустые результаты.
- Фильтры категории и количества гостей; сортировка цены/вместимости.
- Расчёт за весь срок, передача дат и гостей в заявку.
- Пожелания гостя с просмотром в админке.
- Честный статус заявки вместо преждевременного «подтверждено»; переход в личный кабинет.
- FAQ, связь WhatsApp, маршрут до отеля; RU/EN/KG для новых разделов.
- Доработаны мобильные стили, фокус в диалогах, reduced-motion, основной экран и каталог.
- Приблизительный курс USD обозначен знаком ≈. Расчёты брони остаются в KGS.

## Обязательно перед запуском
1. Сделать резервную копию БД и проверить существующие роли администраторов: старые правила могли позволять самоназначение.
2. На тестовой копии, затем в рабочей БД выполнить `supabase/migrations/20261027_security.sql`. Для новой БД достаточно обновлённого `supabase/schema.sql` — защита уже включена.
3. Проверить реальные остатки и установить `rooms.inventory_count` для каждой категории. По умолчанию 1 — консервативный технический предел, НЕ утверждение о количестве номеров отеля. Сверить существующие подтверждённые брони: миграция не исправляет старые пересечения автоматически.
4. Проверить цены, вместимость, фотографии, контакты, условия оплаты/отмены, время заезда. Старые отзывы и маркетинговые утверждения в проекте не верифицированы.
5. Только после миграции развернуть новый frontend (`npm ci && npm run build`). Без миграции новый клиент не сможет гарантировать серверный расчёт цены.
6. Проверить регистрацию, подтверждение email, Google OAuth, разрешённые redirect URL и HTTPS на реальном домене. Включить CAPTCHA / лимиты Auth. Оценить необходимость CSP после инвентаризации внешних фото, шрифтов и карт.
7. Выполнить smoke-test двумя гостевыми аккаунтами и администратором; дополнительно проверить одновременное подтверждение брони в настоящем PostgreSQL. Локальные тесты последовательные, не нагрузочные.

## Проверки
- `npm run typecheck` — успешно.
- `npm run build` — успешно.
- `npm test` — 7 интеграционных тестов SQL на PGlite (PostgreSQL WASM), с эмуляцией auth.uid и ролей; проверены RLS, запрет смены роли/цены/статуса, валидация, отмена, вместимость, соседние даты, лимит заявок. Миграция также повторно применяется поверх новой схемы.
- `npm audit` — 0 известных уязвимостей на момент проверки.
- Полный браузерный тест, реальная отправка брони, OAuth и доставка email в этой среде не выполнялись.

## Ограничения продукта
Сайт принимает заявки, а не мгновенные гарантированные брони. Автоматических писем, SMS, онлайн-эквайринга и синхронизации Booking.com/других каналов нет. Предложения трансфера — пожелания, не подтверждённые услуги. Инвентарь учитывает только подтверждённые брони этой БД; внешние брони нужно заносить/синхронизировать отдельно.
