# Надёжность бронирования — 05.11.2026

## Модель сервиса
Сайт принимает **заявки**, не оплату и не мгновенные подтверждённые брони. `pending` не удерживает инвентарь: несколько гостей могут запросить одну категорию, но подтвердить больше физических номеров, чем `rooms.inventory_count`, нельзя. Полностью занятые подтверждёнными бронями даты отвергаются уже при отправке новой заявки. Выезд исключён из занятого диапазона: один гость может выехать в день заезда следующего.

В рабочей БД при проверке — четыре категории, `inventory_count = 1` у каждой; фактическое количество пока не подтверждено владельцем. Нельзя увеличивать его произвольно. При 1 единице две пересекающиеся подтверждённые брони запрещены; при 2 разрешены две, но не третья. Записи внешних каналов (Booking.com, телефон, стойка регистрации) автоматически НЕ синхронизируются.

## Исправления
- **Конкурентное подтверждение:** транзакционная запись версии инвентаря блокирует категорию. READ COMMITTED видит последнее состояние; REPEATABLE READ / SERIALIZABLE при устаревшем снимке получают ошибку сериализации вместо перепродажи.
- **Повтор запроса:** authenticated RPC `request_hotel_booking` берёт пользователя из auth.uid(), проверяет цену, контактные данные, срок, вместимость и занятость. Идемпотентный UUID хранится с бронью. Повтор с тем же UUID и данными возвращает прежнюю запись, даже если первый HTTP-ответ потерялся.
- **Другой UUID, но тот же активный срок:** серверный запрет дубликата `(user_id, room_id, check_in, check_out)`; второй номер той же категории на те же даты нужно согласовать с отелем. Прямой INSERT из браузера отозван.
- **Цена изменилась:** создание отклоняется. Гость должен обновить тариф, проверить сумму и повторно отправить. Итог успешной заявки отображается из ответа сервера.
- **Кнопка/поля:** синхронный ref-замок предотвращает два вызова до перерисовки React. Во время отправки нельзя менять поля или закрывать окно; через 20 секунд запрос прерывается с безопасным повтором по тому же ключу.
- **Статусы:** устаревшая заявка не подтверждается; завершение до выезда и возврат отменённой/завершённой брони запрещены. Админка отправляет ожидаемый старый статус (compare-and-set), чтобы не перезаписать отмену из другого окна.
- **Количество номеров/вместимость:** нельзя уменьшить ниже уже подтверждённой загрузки. Старые конфликтные данные не исправляются удалением: миграция останавливается.
- **Личный кабинет:** отмена защищена от повторных кликов и изменения статуса в другом окне; ошибка загрузки больше не выдаётся за отсутствие броней.
- **Авторизация:** обновление сессии не скрывает весь личный кабинет; поздний профиль не перезаписывает вручную введённые контакты. Ошибка выхода из аккаунта показывается пользователю.
- **Даты/конфиденциальность:** неполная дата не вызывает падение компонента. Проверка доступности отдаёт только количество, не сведения о других гостях. В sessionStorage хранятся хеш запроса и UUID, не контактные данные.

## Внедрение
1. Резервная копия БД и проверка текущих миграций.
2. Существующая БД: после `20261027_security.sql` применить `supabase/migrations/20261105_booking_reliability.sql`. Новая БД: `schema.sql`, затем новая миграция. Перед применением сверить активные дубликаты/пересечения, ничего автоматически не удалять.
3. Согласованный деплой frontend: старый клиент использует INSERT, новый — RPC. После отзыва INSERT старую версию frontend нельзя возвращать без отдельного совместимого плана отката. Уже открытой старой вкладке понадобится обновление страницы.
4. Smoke-test в рабочем окружении двумя гостевыми аккаунтами и администратором. Нагрузочные тесты выполняются только на изолированной БД, не на данных гостей.

## Автоматические проверки
- `npm test`: клиентские helpers, даты, повтор ключа, статусы и прежний security baseline на PGlite.
- `npm run test:integration`: настоящий временный PostgreSQL (embedded, localhost:55439), независимые соединения и контролируемая гонка. Проверены три уровня изоляции, конкурентная повторная отправка, инвентарь 1/2, соседние даты, отмена, лимиты, права и новые состояния. Кластер удаляется после теста, рабочая БД не используется.
- `npm run test:browser`: локальная сборка с mock API; двойной submit, поля/закрытие во время отправки, потерянный ответ, повтор UUID, изменение тарифа с ручным подтверждением, ранее добавленные проверки страниц номеров.

## Остаточные риски и следующий этап
Это не обещание «исправлены абсолютно все проблемы». Нужны реальные количества номеров, синхронизация каналов и тест почтовых/OAuth-настроек на рабочем домене. Email-уведомления ещё не отправляются автоматически. Заявки не имеют таймера удержания комнаты — такого механизма здесь сознательно нет. Старые снимки каталога могут содержать неактуальные цены; сервер проверяет их перед записью. Тесты PostgreSQL выполняются локально на версии embedded-пакета, а не на production-кластере.
